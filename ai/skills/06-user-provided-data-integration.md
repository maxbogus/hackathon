# Skill: интеграция user-provided данных (per-route разметка)

Использовать через `use_skill("user-provided-data-integration")` когда пользователь
предоставляет данные в свободной форме (таблицы, списки, описания), которые нужно
интегрировать в кодовую базу как hardcoded JSON/Python константы.

## Контекст

На хакатоне пользователь часто предоставляет **доменные знания**:
- Списки объектов вдоль маршрутов (POI, остановки, расписания)
- Координаты, которые он проверил вручную
- Per-route атрибуты (event-venue, спальный, деловой)
- Расписания работы (для open-at-time фич)

Эти данные **ценнее автоматических** (Overpass API возвращает шум, координаты часто
приблизительные). Но они в свободной форме → нужна стандартизация.

## Пошаговая инструкция

### Шаг 1: Получить данные от пользователя

Типичный формат — markdown таблицы в чате:
```
| Объект | Тип | lat | lon |
| МГУ | university | 55.7038 | 37.5306 |
| Лужники | stadium | 55.7155 | 37.5536 |
```

**Что важно зафиксировать:**
- Per-route группировка (какой POI к какому маршруту относится)
- Категория объекта (canonical: school/university/stadium/...)
- Точность координат (если приблизительные — пометить)
- Дополнительные атрибуты (расписание работы, часы пик, сезонность)

### Шаг 2: Определить scope

**Вопросы перед структурированием:**
- Это **per-route** (один POI → один маршрут) или **общий каталог** (POI может быть рядом с несколькими)?
- Дублировать ли POI для каждого маршрута или хранить один POI + список маршрутов?
- Покрыты ли **все 10 маршрутов** или только часть?

**Рекомендация (T-168):**
- Хранить как **общий каталог** (`poi_moscow.json`) — POI один раз, маршруты получают
  его через гео-расчёт
- Это позволяет одному POI быть рядом с несколькими маршрутами (например, Метро
  Университет рядом с route 26 и route 1)

### Шаг 3: Нормализовать категории

Создать **canonical список категорий** в `ml/transit_ai/data/poi_features.py`:
```python
VALID_CATEGORIES = frozenset({
    "school", "university", "stadium", "park", "mall", "theater",
    "culture", "market", "clinic", "hospital", "cinema",
    "train_station", "metro_hub",
})
```

**Если пользователь прислал новую категорию** (например `airport`, `kindergarten`):
1. Обсудить с пользователем — действительно ли это нужно
2. Добавить в VALID_CATEGORIES
3. Добавить в CATEGORY_RADIUS_KM (per-category, по реальным расстояниям)
4. Добавить в CATEGORY_PLURAL (для имени колонки)
5. Запустить sanity-check (см. clinerule 25)
6. Обновить тесты

### Шаг 4: Валидация координат

```python
# Москва bbox
assert 55.0 <= lat <= 56.0, f"Lat out of Moscow: {lat}"
assert 37.0 <= lon <= 38.0, f"Lon out of Moscow: {lon}"
```

Если координаты **точно** из источника — ОК. Если **приблизительные** — добавить
поле `"accuracy_m": 100` в JSON, чтобы будущие изменения могли фильтровать.

### Шаг 5: Записать в JSON

```json
[
  {"name": "МГУ им. Ломоносова", "category": "university", "lat": 55.7038, "lon": 37.5306},
  {"name": "Стадион Лужники", "category": "stadium", "lat": 55.7155, "lon": 37.5536}
]
```

**Рекомендации:**
- Кодировка UTF-8 (для русских названий)
- Compact format (без indentation) — экономит место
- Имена без кавычек-ёлочек («МГУ» → "МГУ им. Ломоносова")
- Сортировка по категориям для читаемости

### Шаг 6: RED-тесты для новых данных

```python
def test_<category>_present_for_route_<n>() -> None:
    """Route N имеет <category> в радиусе."""
    n = count_poi_for_stop(<route_anchor_lat>, <route_anchor_lon>, "<category>")
    assert n >= 1, f"Expected <category> near route N, got {n}"
```

### Шаг 7: Обновить docs (clinerule 25 если новые категории)

Если добавлена **новая категория**:
- Обновить `.clinerules/25-poi-radius-selection.md` — добавить радиус
- Обновить `ml/transit_ai/data/poi_features.py:VALID_CATEGORIES`
- Запустить sanity-check

### Шаг 8: Зафиксировать в ledger

Создать **finding** в `docs/ledger/findings.jsonl`:
```json
{
  "id": "F-NNN",
  "title": "User-provided POI per-route каталог: <N> объектов, <M> категорий",
  "context": "...",
  "evidence": "...",
  "impact": "...",
  "tickets": ["T-NNN"]
}
```

## Типичные ошибки

1. **Игнорировать категории пользователя** — он дал `hospital`, мы маппим в `clinic`.
   Это теряет доменный смысл. Лучше добавить новую категорию.
2. **Дублировать POI для каждого маршрута** — данные раздуваются, обновлять сложно.
   Лучше общий каталог + гео-расчёт per-route.
3. **Не проверять координаты** — могут быть опечатки (55.7038 → 5.7038).
   Всегда sanity-check против bbox.
4. **Забыть про manifest** — при добавлении данных нужно обновить D-NNN в ledger,
   F-NNN в findings, и упоминание в clinerule.
5. **Слать всё в один большой файл** — разделить по scope:
   - `data/external/poi_moscow.json` — POI (общегородские)
   - `data/external/stops_routes.json` — остановки (per-route)
   - `data/external/schedules.json` — расписания работы (когда понадобятся для T-171)
6. **Забыть что user-provided может быть неточным** — координаты проверил человек,
   но он мог ошибиться. Добавить sanity-check перед использованием.

## Когда применять

✅ **Применить:**
- Пользователь прислал список объектов с координатами
- Нужно интегрировать per-route атрибуты (event-venue, спальный, etc.)
- Расписания работы объектов
- Названия/синонимы остановок

❌ **Не применять:**
- Данные из Overpass (уже структурированы)
- Данные из API (2GIS, Яндекс) — лучше парсер, не ручное копирование
- Одноразовые разметки (для отладки, не для production)
