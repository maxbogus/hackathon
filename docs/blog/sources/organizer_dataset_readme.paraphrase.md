## 1. Постановка (смысл)

Задача — **прогноз пассажиропотока трамвайных маршрутов по часам** и файл
`submission.csv` для автоматической проверки.

Главное предупреждение заказчика: **данных за прогнозируемый период нет и не будет**.
Выдано 10 месяцев истории (янв–авг — обучающая часть, сен–окт — тестовая),
а прогноз строится на **ноябрь–декабрь 2025** по скрытому эталону
(`ground_truth`, участникам недоступен). Формулировка заказчика: «вы не сможете
„посчитать“ ответ из данных — его нужно **предсказать**».

## 2. Единица прогноза

`boardings(route, date, hour)` — число **успешных валидаций** (посадок) на маршруте
за календарный час. Маршрут извлекается из поля `ngpt_route` (например,
`"25 трамвай"` → `25`).

## 3. Состав архива

| Элемент | Что это |
|---|---|
| `train.csv` | сырые валидации, январь–август 2025 |
| `test.csv` | сырые валидации, сентябрь–октябрь 2025 |
| `test_submission.csv` | пример файла-решения нужного формата, заполнен baseline-прогнозом |
| `labels/labels_day_train.csv`, `labels/labels_day_test.csv` | готовая почасовая разметка `route;date;hour;boardings` (агрегаты сырых файлов) |
| `spravochniki/` | справочники маршрутов/остановок с координатами (для карты и веб-сервиса) |

## 4. Схема сырых CSV (13 колонок)

Разделитель `;`, UTF-8, первая строка — заголовок. Ключевые поля:
`tran_no` (id транзакции), `device_no` (валидатор), `tran_date_time` (основной
timestamp), `crd_hashcode` (обезличенный хеш карты), `validation_result`
(`1` = успешная посадка), `tran_type_id`, `place_id`, `good_type`, `pass_route`,
`ngpt_route` (источник `route`), `bus_exit_no`, `garage_number`.

Прямо помечены как **ненадёжные/шумные**: `input_date_time` (битые даты —
использовать `tran_date_time`), `pass_route` (шумная цепочка пересадок),
`place_id` («**не остановка**» — площадка/депо, 5–6 значений).

## 5. Маршруты и геопривязка

- В данных 10 маршрутов: `1, 5, 7, 11, 12, 17, 25, 26, 28, 50`.
- Про маршрут `5` — короткая ремарка: **«маршрут `5` встречается редко»**
  (и при этом присутствует в плане оценки).
- Справочники с координатами пересекаются с данными лишь по части маршрутов
  (`{1, 5, 7, 11, 12}`), поэтому остановочная детализация — **«необязательный
  бонус»**, а основная метрика считается по «маршрут × час».

## 6. Формат решения

```
route;date;hour;prediction
```

- `route` — одно из 10 значений; `date` — `2025-11-01 … 2025-12-31`;
  `hour` — `0…23`; `prediction` — число ≥ 0.
- Файл обязан покрывать **полную сетку**: 10 маршрутов × 61 день × 24 часа =
  **14 640 строк**.
- Предложено взять `test_submission.csv` и заменить столбец `prediction`.

## 7. Метрика

```
WAPE       = Σ|y − ŷ| / Σy
WAPE-score = max(0, 1 − WAPE) ∈ [0, 1],  больше — лучше
```

`y` — скрытый эталон ноября–декабря, `ŷ` — прогноз. Метрика устойчива к нулям
и к разбросу объёмов между маршрутами. Пример-baseline в `test_submission.csv`
даёт **≈ 0.48** — его нужно превзойти.

## 8. Особенности данных, о которых предупреждали заранее

1. `input_date_time` местами содержит будущие/битые даты.
2. В файлах есть «суточный хвост» в следующий месяц — агрегировать строго по дате
   из `tran_date_time`.
3. `pass_route` зашумлён — для номера маршрута использовать `ngpt_route`.

## 9. Чего в правилах НЕ было

Ни горизонтов «месяц/год», ни требований к API, дашборду, карте, ролям,
мобильной версии, экспорту отчётов, SLA по времени отклика, ни списка моделей,
ни требования к инфраструктуре. А также не было ни слова про остановочную
метрику как обязательную.
