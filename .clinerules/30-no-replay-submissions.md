# 30-no-replay-submissions.md — Не предлагать варианты, которые уже залиты на платформу

## Контекст (F-061)

Во время сессии T-177 (стратегия зануления) пользователь получил от агента **3 варианта
новых экспериментов**, из которых:

- 2 варианта (B: `pred≤55 + raw`, C: `pred≤55 + bias ×0.5`) уже были залиты или их
  аналоги — `B (blend raw+cal+night zero)` → F-054: **-0.236 ❌**; per-route bias
  calibration уже применена, изменение коэффициента = rehash того же.
- 3 варианта (расширение часов h0-5, h0-6, h6) уже перечислены в **HANDOFF.md
  как "Если есть время"** (T-179) → не новая идея.
- 1 вариант (A: `pred≤55` без calibration) == **уже достигнутый BEST** (F-060).

Проблема: **агент предложил пользователю использовать 1-2 слота на эксперименты,
которые не дадут новой информации** (т.к. результат заранее известен из ledger).
14 слотов / 32 часа до дедлайна. Бессмысленная трата.

**Урок:** когда пользователь говорит "предложи 3 варианта X", агент ДОЛЖЕН
сначала проверить ledger и уже залитые submissions, а не генерировать идеи
из общих соображений. F-061: «Агент предложил 3 варианта стратегии зануления,
которые уже были опробованы в той же сессии — пользователь потратил токены
на разъяснение вместо эксперимента».

## Hard Rules

### R1. Перед "предложи варианты" — ОБЯЗАТЕЛЬНАЯ проверка ledger

Перед тем как предложить **что-либо как вариант эксперимента** для заливки на
платформу хакатона:

1. **Прочитать** `docs/ledger/findings.jsonl` (последние 7-14 дней).
2. **Прочитать** `docs/HANDOFF.md` (секции "Не делать" + "Если есть время").
3. **Проверить** `predictions/*.json` manifests на наличие аналогичной стратегии.
4. **Проверить** `docs/backlog/tickets/T-NNN-*.md` — там может быть уже
   запланированный эксперимент с явным описанием.

Только после этого — генерировать список вариантов.

### R2. Каждый предложенный вариант должен иметь атрибут `novelty`

В каждом варианте в списке для пользователя атрибут `novelty` явно указывает:

| `novelty` | Значение | Действие |
|---|---|---|
| `validated` | Уже залит, есть platform score | ❌ Не предлагать как новый (R3) |
| `in_progress` | В работе, ожидается score | ⚠️ Упомянуть как pending, не повторять |
| `partial` | Частично сделан (компоненты, не вся стратегия) | ⚠️ Указать какой компонент уже проверен |
| `untested` | Не было залито в этом или близком виде | ✅ Можно предлагать |
| `queued` | Есть в BACKLOG тикете (например T-179) | ⚠️ Сослаться, не дублировать |

### R3. Запрет на дубликаты стратегий

**НЕЛЬЗЯ** предлагать вариант, если он или его прямой аналог (тот же pred≤X,
тот же hours range, тот же blend-component) уже залит с известным platform
score в `docs/ledger/findings.jsonl`.

Прямые аналоги:
- `pred≤N` h0-4 для разных N → если **любой** из {20, 25, 35, 45, 50, 55, 100}
  уже залит, остальные N нельзя предлагать как «новые» — это sweep вокруг peak.
- `bias calibration × factor` → даже ×0.5/×0.7 — это **тот же** компонент (raw+cal).
- Расширение hours h0-N → если N=5 уже залит и известен score, h0-6 не новая идея.

### R4. Обходной путь: «всё уже проверено» = СТОП

Если после R1-R3 осталось **0 untested вариантов**, агент ОБЯЗАН явно сказать:

```
Все доступные варианты в этой стратегии исчерпаны (см. ledger):
- X залит → Y (F-NNN)
- Z залит → W (F-NNN)

Следующие гипотезы ВНЕ этой стратегии (другие тикеты: T-178, T-179, T-180, ...).
Продолжать эти эксперименты = трата слотов. Стоп?
```

…а не продолжать генерировать «варианты» из тех же компонентов.

### R5. «X без Y» ≠ новый эксперимент, если уже в BACKLOG

Если вариант = «убрать компонент, который уже в BACKLOG как T-NNN» (например,
T-178 «убрать per-route bias calibration»), это **не** «новый вариант» — это
**уже существующий тикет**. Сослаться, не предлагать как 3 новых опции.

### R6. Когда R1-R3 можно ослабить

Только если:
- Пользователь явно попросил «попробуй ещё раз, может быть drift» / «reanalyze».
- Новый submission_pipeline (R-Fast) дал ранее не виданный компонент
  (новая модель, новый blend, новый submission_id).
- Пользователь добавил новые данные (например, новый реальный датасет).

В остальных случаях — R1-R3 строго.

## Правило в чате: формат ответа «предложи N вариантов»

Когда пользователь говорит «предложи N вариантов X», формат:

```markdown
Прошёл по ledger (last 7d) + HANDOFF:

**Уже залито** (НЕ предлагаю, см. F-NNN):
- [компонент] → [platform score]

**Backlog queued** (уже запланировано):
- T-NNN: [краткое описание]

**Untested варианты**:
1. **A** [untested] <конкретное описание>
   novelty: комбинация [X+Y] не встречалась в ledger
   risk: какая платформа может вернуть (-regress / +improve)
2. **B** [untested] ...

**Если A и B слишком похожи на уже проверенное** — СТОП, лучше:
- переключиться на T-NNN (другая стратегия)
- либо явно попросить re-explore конкретное направление
```

Это даёт пользователю СРАЗУ контекст «что уже известно», и он не тратит
токены на вопросы «а это уже пробовали?».

## Антипаттерны (что я делал НЕ ТАК)

### F-061 / аналогичный кейс

Я предложил:
- A: pred≤55 БЕЗ bias calibration
- B: pred≤55 + raw (без calibration) для проверки эффекта bias
- C: pred≤55 + меньший bias коэффициент (×0.5)
- D: pred≤55 h0-4 + pred≤30 h5
- E: pred≤55 h0-4 + pred≤30 h0-5
- F: pred≤55 h0-4 + pred≤20 h6

Из них **все 6 вариантов — replay/перебор** уже залитых:
- A == F-060 (current best)
- B == F-054 «blend raw+cal» (заливался, дал -0.236 ❌)
- C == калибровочный sweep, либо A (если ×0), либо B (если ×0)
- D-F == T-179 «расширение часов» (есть в HANDOFF «Если есть время»)

Пользователь должен был объяснять, что это **всё уже проверено**.
Трата: ~500 токенов контекста + 1-2 потенциальных слота впустую.

### «3 варианта = 3× один компонент с разными N»

```markdown
НЕПРАВИЛЬНО (3 варианта одного sweep):
A: pred≤45 h0-4
B: pred≤50 h0-4
C: pred≤55 h0-4

ПРАВИЛЬНО (3 разных направления):
A: pred≤55 + расширить hours h0-5 (NEEDS HOURLY ANALYSIS — T-179)
B: T-178 без bias calibration (QUEUED в BACKLOG)
C: T-180 weekends/holidays zero (QUEUED в BACKLOG)
```

«3 варианта» должны быть **3 разных гипотезы из разных семейств**,
а не 3 точки вокруг уже найденного peak.

## Workflow: правильный цикл «предложи варианты»

1. User: "предложи 3 варианта X"
2. Read: docs/ledger/findings.jsonl (last 14d)
3. Read: docs/HANDOFF.md (sections: Не делать, Если есть время)
4. Read: docs/backlog/tickets/T-*.md (status: ready|in-progress)
5. Read: predictions/*.json (последние 5 манифестов)
6. Classify вариантов по novelty (R2)
7. Если <3 untested — СТОП + сообщить (R4)
8. Если ≥3 untested — предложить, но с маркировкой
9. Каждый вариант: novelty + обоснование «почему не replay»

## Don't do

- Предлагать sweep вокруг найденного peak как «новые варианты»
- Предлагать «X без Y» / «X с Y'» если Y/Y' уже в BACKLOG как тикет
- Генерировать «3 варианта» из одного компонента без проверки ledger
- Считать «backlog queued» за «новый вариант для заливки»
- Пропускать R1 (чтение ledger) ради скорости ответа
- Молчать о том, что варианты исчерпаны — пользователь должен это знать
